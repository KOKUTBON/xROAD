# Institutional deployment guide

The institutional stack supports a dedicated installation per institution. It
requires HTTPS, authenticated internal API access, an institution-managed OIDC
provider, and mounted secrets. This is a deployment foundation; completion of
these steps is not certification or acceptance for production use.

Shared multi-institution database isolation and offline map operation still need
implementation and verification. Use a separate stack and database per institution.
The maps currently contact external tile providers; do not describe this release
as air-gapped or as having zero external dependencies.

For standard product profiles, organization/jurisdiction configuration, and the
implementation acceptance package, see
[institution product implementation](institution-product-implementation.md).

## 1. Prepare institutional configuration

Copy `configs/institutional_tenant.example.toml` to a deployment-specific file
under `configs/`, and review the institution, branding, units, jurisdiction, and
privacy settings. Include a versioned `[deployment]` profile and real organization/jurisdiction IDs. Production rejects legacy profiles. Configuration checks are not a security or compliance audit.

```bash
python3 infra/scripts/bootstrap_institution.py \
  --config configs/my_institution.toml --generate-env --generate-secrets
```

The bootstrapper creates `infra/docker/.env.institution` with mode `0600` and
random, independent database/storage password files. It refuses to overwrite
existing settings or secrets. If an environment file already exists, review and
migrate it using `.env.institution.example`; use `--generate-secrets` separately
only for a fresh installation. No existing local deployment is modified by this
repository change.

Alternatively, copy `.env.institution.example` to `.env.institution`, set its
permissions to `0600`, and have your secret manager provision all secret files.

## 2. Provision secrets and TLS

The sample template uses the paths below (relative to `infra/docker/`). The bootstrapper uses `secrets/<institution-id>/` instead; follow its generated file paths:

| File | Provisioning |
| --- | --- |
| `secrets/institution/postgres_password` | Generated by bootstrapper or supplied by secret manager; minimum 24 characters |
| `secrets/institution/minio_password` | Independent generated/managed secret; minimum 24 characters |
| `secrets/institution/oidc_client_secret` | Actual confidential web client's secret from the institution's IdP; minimum 24 characters |
| `secrets/institution/tls_certificate` | PEM certificate chain issued for the public hostname |
| `secrets/institution/tls_private_key` | Matching PEM private key |

These files are mounted with [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).
Passwords are absent from the Compose environment and image build context.
Application processes load credentials internally at startup; administrators with
container/host access can still inspect process memory/environment. File-backed
Compose secrets are not an encrypted vault: the institution must secure the host
and arrange storage encryption, backup protection, access control, and rotation.

Keep the parent secret directory owned by the deployment operator with mode
`0700`. File-backed Compose mounts preserve host file permissions, so files must
be readable by the appropriate container user. Bootstrap-generated password files
use `0444` inside that private directory, because Postgres and application users
have different UIDs. Use ACLs or managed mounts instead if institutional policy
requires more restrictive file permissions. Do not publish or commit these files.

Supply TLS files from the institution's PKI or certificate manager. The gateway
uses [Caddy's explicit certificate/key configuration](https://caddyserver.com/docs/caddyfile/directives/tls);
it does not request certificates from an external ACME service. The operator owns
renewal. Validate certificate hostname, expiry, chain, and key match before launch.

## 3. Configure identity and the public hostname

Edit `.env.institution`:

```dotenv
ROAD_RISK_HOSTNAME=road-risk.your-agency.gov
ROAD_RISK_API_AUTH_ENABLED=true
ROAD_RISK_API_AUTH_JWKS_URL=https://sso.your-agency.gov/realms/road-risk/protocol/openid-connect/certs
ROAD_RISK_API_AUTH_ISSUER=https://sso.your-agency.gov/realms/road-risk
ROAD_RISK_API_AUTH_AUDIENCE=road-risk-api
ROAD_RISK_API_AUTH_CLIENT_ID=road-risk-api
ROAD_RISK_WEB_OIDC_CLIENT_ID=road-risk-web
```

Register a confidential web client with the exact redirect URI
`https://road-risk.your-agency.gov/api/auth/callback`. Configure its allowed logout
redirects for that origin. Provision its actual secret in the configured file.
For providers other than Keycloak, configure the authorization, token, and logout
endpoint overrides in the template (HTTPS required). Configure your IdP to issue
API access tokens with the required audience, supported roles, `organization_ids`,
and `municipality_ids`. See `apps/api/auth.py` for the actual role matrix;
`municipal_admin` is not a supported role name.

The institutional stack forces API authentication on. A production API launched
outside Compose also refuses to start without authentication, HTTPS issuer/JWKS,
and an explicit audience. Public endpoints remain available under their existing
publication policy. This change does not certify all publication privacy controls.

## 4. Validate and initialize

```bash
docker compose --env-file infra/docker/.env.institution \
  -f infra/docker/docker-compose.institution.yml config --quiet

docker compose --env-file infra/docker/.env.institution \
  -f infra/docker/docker-compose.institution.yml build

# Check secret loading and security configuration before starting the full stack.
docker compose --env-file infra/docker/.env.institution \
  -f infra/docker/docker-compose.institution.yml run --rm --no-deps api --check

docker compose --env-file infra/docker/.env.institution \
  -f infra/docker/docker-compose.institution.yml run --rm --no-deps web --check

# Fresh database setup; upgrades require backup and migration review first.
docker compose --env-file infra/docker/.env.institution \
  -f infra/docker/docker-compose.institution.yml up -d postgres redis minio

docker compose --env-file infra/docker/.env.institution \
  -f infra/docker/docker-compose.institution.yml run --rm api \
  alembic -c alembic.ini upgrade head

docker compose --env-file infra/docker/.env.institution \
  -f infra/docker/docker-compose.institution.yml up -d
```

The generated settings use a dedicated `ROAD_RISK_INSTITUTION_DATA_DIR` and a unique `ROAD_RISK_DEPLOYMENT_NAME`. Prepare that data directory and the public `ROAD_RISK_INSTITUTION_BRAND_DIR` directory with the required container read/write permissions and approved local data; do not reuse it across institutions. Compose isolates named volumes and networks by deployment name.

Only the gateway publishes a host port (`443` by default). Web, API, database,
Redis, and MinIO do not publish ports. Browser API traffic uses the same HTTPS
origin through `/api/backend`; the web server forwards bearer tokens to FastAPI.
Gateway responses include HSTS; HTTP service is intentionally not exposed.
API, worker, and web processes run without root, with privilege escalation disabled
and Linux capabilities dropped. Ensure the mounted `data/` directory grants their
container users the required read/write access; do not make it world-writable.

Configure internal DNS, firewall rules, and trust stores so server-side requests
can reach the IdP over HTTPS. Container-to-container traffic inside this dedicated
host uses HTTP; if policy requires internal encryption, add a separately reviewed
mTLS/service-network configuration before acceptance.

After launch, check the public page and branding, SSO login/logout, denied
unauthenticated internal requests, scoped access, ingestion and workers, and
reports. Verify with a trusted client using the institution's CA bundle; do not
use TLS verification bypasses for acceptance.

## 5. Operational acceptance and existing deployments

Do not replace files or start this stack against an existing institution until
its backup, migration plan, service identity permissions, and certificate setup
have been reviewed. Changing a password file does not rotate credentials in an
already-initialized PostgreSQL database; rotate the database credential first in a
controlled procedure, update the file, and recreate dependent application services.
Recreate MinIO/web services after storage/client-secret rotation. Reload/recreate
the gateway after TLS renewal.

Test backups and restoration, load and recovery behavior, local model evaluation,
publication privacy controls, and accessibility. Assign operational and data
owners and complete the institution's applicable governance assessment. This
stack's security defaults do not establish regulatory certification, model
validity in a new jurisdiction, shared-tenant isolation, or offline readiness.
